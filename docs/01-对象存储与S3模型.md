# 01 · 对象存储与 S3 模型

## 1.1 对象存储与文件系统

| 维度 | 文件系统 | 对象存储 |
|---|---|---|
| 组织方式 | 目录树，目录是真实实体 | 扁平命名空间，Key 里的 `/` 只是字符串 |
| 访问方式 | `open/read/write/seek` | HTTP + S3 API（GET/PUT/DELETE/LIST） |
| 扩展方式 | 纵向扩容、共享存储 | 横向扩展，多节点/多磁盘 |
| 元数据 | 有限 | 每个对象可带用户元数据、标签、Content-Type |
| 修改 | 可随机写 | 对象整体覆盖，不能原地修改某几个字节 |
| 典型场景 | 程序配置、日志、数据库文件 | 图片、视频、备份、数据湖、静态资源 |

对象存储的核心取舍是：**用简单的 PUT/GET 语义换取近乎无限的扩展能力**。因此没有真正的“重命名”和“追加写”；重命名是复制+删除，追加写是重新上传整个对象。

## 1.2 核心概念

| 概念 | 说明 |
|---|---|
| Bucket（桶） | 对象的顶层容器，全局命名空间的一部分；本机名如 `learn-object` |
| Object（对象） | 数据 + 元数据；由 Bucket + Key 唯一确定 |
| Key | 对象名，例如 `docs/2026/report.pdf`；`/` 只是普通字符 |
| Prefix | Key 的前缀，用于模拟“目录”和批量列举 |
| ETag | 服务端计算的对象标识；普通 PUT 通常是 MD5，分片上传带 `-N` 后缀 |
| Version | 开启版本控制后，每次覆盖/删除产生新版本 |
| Delete Marker | 版本化桶中“删除”产生的特殊版本，当前版本变为“不存在” |
| User Metadata | 自定义 `x-amz-meta-*` 键值，写入后随对象保存 |
| Object Tags | 最多 10 个键值标签，可用于生命周期、权限、成本分析 |
| Bucket Policy | JSON 授权策略，可开放匿名读、限制前缀、拒绝非 TLS 请求 |
| Object Lock | WORM（一次写入多次读取）保留策略，分 GOVERNANCE / COMPLIANCE |

示例：

```text
s3://learn-object/docs/hello.txt
     └─ bucket      └─ key（前缀 docs/）
```

> 目录不是真实存在的。控制台里看到的文件夹，是客户端按 `/` 聚合出来的视图。

## 1.3 S3 协议与签名

S3 是一个 HTTP API。最常用的请求：

```http
PUT    /bucket/key          上传/覆盖
GET    /bucket/key          下载
HEAD   /bucket/key          获取元数据（SDK 的 statObject）
DELETE /bucket/key          删除
GET    /bucket?list-type=2  列举对象
PUT    /bucket?versioning   配置版本控制
PUT    /bucket?lifecycle    配置生命周期
```

**为什么直接访问 `http://127.0.0.1:9000/` 返回 403？**

因为请求没有携带身份签名。S3 用 **AWS Signature Version 4（SigV4）** 对请求签名，签名材料包括：

- Access Key / Secret Key
- HTTP 方法、路径、查询参数
- Host 头
- 请求体哈希
- 时间戳（`x-amz-date`）
- Region（MinIO/Silo 默认 `us-east-1`）

任何一项不一致都会得到 `SignatureDoesNotMatch`。常见原因：系统时间偏差过大、endpoint 写错、经过反向代理后 Host 改变、URL 中的查询参数被改写。

**预签名 URL** 是把签名结果放进 URL 的查询参数，让没有密钥的客户端在有效期内访问某个对象：

```text
http://127.0.0.1:9000/bucket/key?X-Amz-Algorithm=...&X-Amz-Signature=...
```

它只授予单个方法（GET/PUT）和单个对象的临时权限，最长 7 天。预签名 URL 不是“公开桶”，泄露后任何人在有效期内都能使用。

## 1.4 Silo 与 MinIO

- **MinIO**：高性能 S3 兼容对象存储，社区版曾是最流行的自建方案。
- **Silo**：PGSTY 维护的 MinIO 社区分支，保留开源的完整控制台、二进制发布与安全修复；协议和存储格式不变，兼容 `MINIO_*` 环境变量、`minio_*` 指标、`/minio/*` 路由和 `.minio.sys` 数据目录。
- 本项目运行的是 Silo，但代码全部使用标准 S3 API 和 MinIO Java SDK，迁移到 MinIO/AWS S3 只需改 endpoint、凭据和 region。

本机布局：

| 组件 | 地址 | 说明 |
|---|---|---|
| S3 API | `http://127.0.0.1:9000` | SDK、curl、预签名 URL 使用 |
| Web 控制台 | `http://127.0.0.1:9001` | 浏览器登录、上传、查看指标 |
| 数据目录 | `D:\ProgramFiles\silo_20261112000000.0.0_windows_amd64\minio\` | 包含 `.minio.sys` 等内部数据 |

启动命令（由本机进程信息确认）：

```bat
silo.exe server D:/ProgramFiles/silo_.../minio/ --console-address :9001
```

> 记住：**9000 是 API，9001 是控制台**。SDK 连 9001 会得到控制台 HTML，表现为各种奇怪的解析错误。

## 1.5 一致性与原子性

对象存储的语义比文件系统简单，但需要理解几个关键点：

- **PUT 是原子的**：客户端要么看到旧对象，要么看到完整的新对象，不会看到“写了一半”的对象。
- **新对象读后一致**：PUT 成功后立即 GET 通常能读到新内容（MinIO/Silo 提供强一致语义）。
- **覆盖写**：同名 Key 的 PUT 会替换对象；开启版本控制后，旧内容保留为历史版本。
- **LIST 是前缀扫描**：返回顺序按 Key 字典序，不保证与上传时间一致。
- **删除**：未开版本控制时直接删除；开启后默认生成 Delete Marker，历史版本仍在。
- **没有跨对象事务**：批量操作不是原子的，失败后需要重试/补偿。

## 1.6 纠删码（Erasure Coding）

MinIO/Silo 使用纠删码而不是传统 RAID：

- 对象被切成数据块和校验块，例如 `EC:4` 表示 4 个数据块 + 4 个校验块。
- 最多可以丢失与校验块数量相同的磁盘/节点，数据仍可恢复。
- 读取时并行读取多个块，重建缺失块；后台 `healing` 会修复故障磁盘上的数据。
- 单机单盘学习环境没有冗余；生产至少需要多块磁盘/多节点，并规划故障域。

纠删码的代价是 CPU 和网络开销；它解决的是“磁盘/节点故障”，**不是备份**。误删、勒索软件、逻辑损坏仍需要独立备份。

## 1.7 常用限额

| 项目 | 限制 |
|---|---|
| 单次 PUT 对象大小 | 5 GiB |
| 单个对象最大 | 5 TiB |
| 分片大小 | 5 MiB – 5 GiB（最后一片可小于 5 MiB） |
| 单对象分片数 | 最多 10000 |
| 预签名有效期 | 1 秒 – 604800 秒（7 天） |
| 对象标签 | 最多 10 个 |
| 桶名 | 3–63 字符，小写字母/数字/点/连字符，不能以点或连字符开头结尾 |

## 1.8 术语表

| 术语 | 含义 |
|---|---|
| S3 | Amazon Simple Storage Service 的 API 标准，已成为对象存储事实标准 |
| SigV4 | AWS Signature Version 4，S3 请求签名算法 |
| Presigned URL | 带签名的临时 URL |
| Multipart Upload | 分片上传，大文件拆成多个 Part 后合并 |
| WORM | Write Once Read Many，对象锁的典型场景 |
| Governance / Compliance | 两种保留模式；前者可被有权限者绕过，后者到期前不可删除 |
| Legal Hold | 法律保留，独立于保留期限，开启后阻止删除 |
| Lifecycle | 生命周期规则，按天数过期、清理分片、转换存储类型 |
| SSE-C / SSE-S3 / SSE-KMS | 服务端加密的三种密钥管理方式 |
